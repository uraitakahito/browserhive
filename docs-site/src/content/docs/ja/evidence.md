title: 証拠としてのアーカイブ
description: BrowserHive が証拠利用に向けて目指していること、現時点で成立している性質、まだ成立していない性質
---

BrowserHive は、後から誰かが責任を持って提示できるアーカイブ —— 単に再生できる
だけでなく、**証拠として差し出せるもの** —— を目指しています。

このページはその現在地を記したものです。**方向と現状の説明であって、今日生成された
アーカイブがどこかで証拠として採用されるという主張ではありません。** 証拠利用が
前提とする性質のうち、まだ実装されていないものがいくつもあり、それらは成立している
ものと同じだけ率直に列挙してあります。

:::caution
本ページは法律実務の助言ではありません。特定のアーカイブが特定の手続で使えるか
どうかは、弁護士に、最終的には裁判所に委ねられる問題です。
:::

## 「真正性」が実際に覆う範囲

最も多い誤解を先に書きます。ここを取り違えると、作るべきものを丸ごと間違えるからです。

電子的な記録に関する法的枠組みが認証しているのは、**記録と、それを作成した人**で
あって、**内容の出所ではありません**。

- 米国の連邦証拠規則では、
  [Rule 902(13) および 902(14)](https://www.law.cornell.edu/rules/fre/rule_902)
  により、電子的な記録は**資格ある者による認証書**によって自己認証できます。そこで
  ハッシュ値が果たす役割は「提出物が取得物と同一の複製であること」を示すことであり、
  **原本がどこから来たか**ではありません。
- 日本では、
  [電子署名法 3 条](https://laws.e-gov.go.jp/law/412AC0000000102)
  により、本人による電子署名がある電磁的記録は**真正に成立したもの**と推定されます。
  ここでいう「真正に成立した」とは、**作成者の意思に基づいて作成されたこと**
  （＝他人によって偽造されたものではないこと）であり、その内容が外部のウェブサイトを
  正しく写しているかどうかは別の問題です。

したがって、アーカイブの中にどれだけ暗号を積んでも「このページは確かにあのサーバから
来た」ことは証明できません。代わりに作れるのは、**精査に耐えるプロセス** ——
署名され、時刻が裏づけられ、自らの欠落について正直で、第三者が再現できる記録です。

BrowserHive はこの軸に沿って進めています。

## 現時点で成立していること

| 性質 | 実現方法 | 参照 |
| --- | --- | --- |
| アーカイブが署名される | `signing: true` により、`datapackage.json` の `sha256:` に対する [wacz-auth](https://specs.webrecorder.net/wacz-auth/0.1.0/) 署名を要求し、`datapackage-digest.json` として格納する | [WACZ に署名する](/signing/) |
| 署名鍵をキャプチャワーカーが持たない | ハッシュを署名サービスに送り、返ってきたものを格納するだけ。ワーカーが侵害されても第二のアーカイブを偽造できない | [WACZ に署名する](/signing/) |
| 署名を受け取るだけでなく検証する | アーカイブが署名済みを名乗る前に 4 つ確認する。署名がこのキャプチャの hash を覆っているか、証明書が設定した root に繋がるか、名乗ったドメイン向けに発行されているか、タイムスタンプがこの署名を覆っているか。結果は個別に記録し、`skipped` は合格ではない | [WACZ に署名する](/signing/) |
| 観測した TLS を記録する | HTTPS ホストごとに protocol・cipher・subject・issuer・有効期間、および証明書チェーンの実体。出所の証明にはならない（証明書は公開情報）が、`issuer` は傍受で変わる値であり、有効期間は取得時刻と突き合わせられる | [キャプチャ結果](/capture-results/) |
| 署名が fail-closed | 署名が必要なキャプチャで取得できなければキャプチャ失敗となり、成果物は保存されない。何を提供するかは配備ごとに `--signing-policy` で決める | [WACZ に署名する](/signing/) |
| 署名時刻を裏づけられる | 署名サービスが付与した場合、`signedData` は RFC 3161 タイムスタンプトークンを持つ（開発用サービスは常に付与する）。BrowserHive は返ってきたものをそのまま格納する | [WACZ に署名する](/signing/) |
| アーカイブが自らの欠落を申告する | `completeness` が**取得できなかったもの**を記録する（`304` で本文が得られなかったもの、サイズ上限で切り詰めたもの） | [キャプチャ結果](/capture-results/) |
| どこで打ち切ったかを申告する | `coverage` がスクロールの到達点を記録する。ページのどこまで実際に到達したか | [キャプチャ結果](/capture-results/) |
| 設定を「要求」ではなく「適用結果」で記録する | `settings` は**実際に効いていた**ビューポート・キャッシュ・DPR・アーカイブモードを保持する。観測条件が読み取れる | [キャプチャ結果](/capture-results/) |
| 生成したビルドが機械可読 | `build` にバージョン・リビジョン・ビルド時刻、`browser` に Chromium の製品文字列 | [キャプチャ結果](/capture-results/) |
| 署名が無い場合、その理由が残る | `SignatureReport` が「誰も要求しなかった」と「要求したが失敗した」を区別し、理由を記録する | [WACZ に署名する](/signing/) |
| 暗号操作を手で再現できる | 開発用署名サービスは `--explain` で実行した `openssl` コマンドをすべて印字する。第三者がツールを信用せずに各段階を追える | [capping](https://uraitakahito.github.io/capping/) |
| 仕様との差異が明文化されている | 仕様が示す方法と別のことをしている箇所は、後から発見されるのではなく理由付きで公開されている | [仕様の実装状況](/spec-coverage/) |

後半のいくつかは見た目より重要です。**取得できなかったものを自分から申告している
アーカイブ**は、黙っていて後から欠落が判明するアーカイブより、はるかに擁護しやすい。
この性質はこのプロジェクトで既に一貫して守られており、証拠利用はその重要度を
上げるだけです。

## まだ成立していないこと

以下が現時点の欠落です。**実装の難易度ではなく、証拠利用にとっての重大さ**の順に
並べています。

### 開発用の署名サービスは実署名に使えない

開発で使う署名サービスは自前の CA を発行し、生成するファイルにはすべて
`insecure-dev-` という接頭辞が付きます。この命名は意図的で、読む人が最初に目にする
場所に置いてあります —— そして文字どおりの意味です。

**必要なもの:** 実在の認証局が発行した署名証明書と、認定された時刻認証局。
`WaczSigner` は既にポートとして切られているため差し替え口は存在しますが、
実サービスに対して検証された実績はありません。

### 操作者の同一性がアーカイブに結びついていない

アーカイブはどのビルドが生成したかを記録しますが、**誰が実行したか**は記録しません。
FRE 902(13)/(14) が想定する認証書は人が作成するものであり、現在アーカイブの中には
それをキャプチャに結びつけるものが何もありません。

**必要なもの:** 要求者の同一性をアーカイブに持ち込み、署名の対象に含める仕組み。

### 名前解決の結果を記録していない

そのホストに対して実際にどのアドレスが応答したかの記録がありません。**DNS の
差し替えは証明書の差し替えより事後の検出が困難**であり、その意味で証明書と同等以上に
重要です。

**必要なもの:** TLS の観測結果と併せて解決済みアドレスを記録すること。

### 保存後のアーカイブが差し替えから守られていない

成果物は S3 互換ストレージにアップロードされます。署名により改変は**検出可能**ですが、
オブジェクトの上書きや削除を**防ぐ**仕組みはなく、それが起きたことを記録する仕組みも
ありません。

**必要なもの:** ストレージ側の不変性（オブジェクトロック等）と、文書化された保持方針。
[ストレージ](/storage/) を参照してください。

### 監査証跡が無い

誰がキャプチャを要求し、誰が後から取り出したかの記録がありません。
**chain of custody（証拠の連鎖）**はプロセスを擁護可能にする要素の一つですが、現状では
システムの外側から再構成するほかなく、再構成できるとも限りません。

**必要なもの:** 要求と取り出しを対象とする監査ログ。

## BrowserHive が主張しないこと

**アーカイブが証明する範囲を過大に述べることは、上記のどの欠落よりも大きなリスク**です。
過大な主張が一点でも精査で崩れると、正しい主張の信用まで巻き添えになります。
以下はこのプロジェクトが避ける表現と、代わりに用いる表現です。

| 用いない | 用いる |
| --- | --- |
| 証明書により取得元の真正性を保証します | 取得時にブラウザが観測した TLS 情報を記録しています |
| 改ざん不可能なアーカイブです | 署名により改変を**検出**できます |
| 法的証拠として有効です | 証拠として提出する際に必要な情報を記録します（採否は裁判所の判断です） |
| ページを完全に保存しました | 取得できなかったものは `completeness` に記載しています |

同じ規律を命名にも適用します。観測した TLS を表すフィールドは保証ではなく**観測**に
ちなんだ名前を用います。`certificateProof` のような名前は、実装が果たしていない
約束をその名前自体が始めてしまうからです。

## 着手の順序

1. **署名を信頼できるものにする。** fail-closed 化と受信した署名の検証は実装済みです。
   残るのは実在の認証局、認定された時刻認証局、そして操作者の同一性をアーカイブに
   結びつけること。これらが成立するまで、後続の項目を積んでも効果は限定的です。
2. **取得時の文脈を記録する。** TLS 証明書チェーンと解決済みアドレスを、
   参照ではなくアーカイブ自身に格納する。
3. **取得後のアーカイブを守る。** ストレージの不変性、保持方針、監査証跡、
   そして第三者がたどれる検証手順書。
